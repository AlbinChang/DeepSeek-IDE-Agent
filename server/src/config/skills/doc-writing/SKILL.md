# 文档写作规范

## 1. 素材充分性优先

动笔前先判断现有素材是否足以支撑用户要求的字数、深度和章节结构。素材不足时必须继续探索：优先读取工作区已有 README、技术文档、业务文档、代码、配置、日志、数据文件和相关上下文；必要时用浏览器抓取用户指定或权威公开来源。

把新增材料转化为事实、案例、数据、对比、步骤、风险、边界条件和建议，而不是形容词。

## 2. 禁止填充式写作

禁止以下行为：

- 同义反复、段落重复、章节重复；
- 模板化空话、正确的废话、无信息量的过渡段；
- 无依据推测、虚构事实/数据/案例/引用；
- 用「随着…的发展」「众所周知」等套话堆砌篇幅。

确实无法获取足够材料时，说明材料缺口并请求用户补充，或明确标注「待确认」，不得编造。

## 3. 一致性

- 关键结论、数据口径、统计时间、主体名称、范围边界必须全篇一致。
- 同一概念只用一种术语；缩写首次出现时给出全称。
- 数据来源与时间点必须可追溯。

## 4. 结构

1. 先给结论/摘要，再给论据与细节。
2. 章节层级 ≤ 3 级，标题必须能独立表达信息，避免「概述」「其他」这类空标题。
3. 长文档开头提供目录或阅读路径。
4. 复杂流程/架构优先用图（见 `svg-diagram` 技能），不要用大段文字描述结构。
5. 表格用于对比与结构化数据，不要用表格承载长段落。

## 5. 交付前自检

1. 材料是否覆盖了全部承诺的章节与论点？
2. 是否存在重复段落、前后矛盾、未兑现的承诺？
3. 每个数据/事实是否有来源或标注为待确认？
4. 目录、编号、交叉引用是否与正文一致？
5. 编码为 UTF-8，中文无乱码（`file_write` 必须传 `encoding: "utf-8"`）。

## 6. 参考资料归档

- 下载的技术文章、白皮书、API 规范、研究论文等有长期参考价值的材料属于项目知识资产，统一放 `docs/references/<主题>/`。
- 临时中间产物放 `.temp/`；最终交付文件禁止写入 `.temp/`。
- 网页内容转 Markdown 时按 `web-research` 技能执行（图片本地化、禁用截图代内容）。
