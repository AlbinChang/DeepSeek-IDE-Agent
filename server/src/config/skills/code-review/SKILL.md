# 代码检视规范

## 1. 检视前先确定范围

1. 明确检视对象：指定文件/目录、当前 diff、最近 N 个提交、或整个模块。
2. 读取真实代码后再判断，禁止凭文件名、函数名或历史记忆推测实现。
3. 改动类检视优先看 diff 与上下文（调用方、被调用方、配置、测试），避免只看被改动的行。
4. 范围过大时用 `append_todo` 拆分模块逐个检视，禁止抽样后就下总体结论。

## 2. 检查维度（逐项过一遍）

1. **正确性**：逻辑分支是否完备、边界条件（空值/0/负数/超长/超时/并发）、循环终止、状态机迁移、类型转换与精度。
2. **错误处理**：异常是否被吞掉、失败路径是否有回滚/清理、错误信息是否可定位、重试是否幂等。
3. **安全**：路径穿越、命令注入、SQL/模板注入、越权访问、敏感信息硬编码或写入日志、未校验的外部输入。
4. **并发与资源**：竞态、死锁、连接/句柄/临时文件未释放、无界队列与内存增长。
5. **性能**：不必要的 O(n²) 循环、循环内 IO/查询、重复计算、缺失索引、过大 payload。
6. **可维护性**：函数过长、职责混杂、重复实现、魔法数字、命名与注释失真、废弃代码残留。
7. **一致性**：与项目既有约定（目录结构、错误码、日志格式、编码、依赖版本）是否一致；接口/配置变更是否同步文档与测试。
8. **测试**：关键路径是否有测试覆盖、测试是否断言行为而非实现细节、是否存在被跳过的用例。

## 3. 问题分级

- **P0 阻断**：数据损坏、安全漏洞、崩溃、主流程不可用。
- **P1 严重**：明确的功能错误、资源泄漏、无错误处理的失败路径。
- **P2 一般**：边界条件缺失、性能隐患、可维护性明显问题。
- **P3 建议**：命名、注释、格式、可读性优化。

## 4. 报告格式

先给结论，再给清单：

```
## 检视结论
（通过 / 有条件通过 / 不通过；一句话总体判断）

## 问题清单
| # | 级别 | 位置 | 问题 | 影响 | 建议修复 |
|---|------|------|------|------|----------|
| 1 | P1 | src/x.ts:42 | ... | ... | ... |

## 未覆盖范围
（本次未检视的部分，避免给出过度承诺）
```

- 每条问题必须能定位到文件与行号，并说明为什么是问题、会导致什么后果。
- 只报告有把握的问题；不确定的写入「待确认」，不要用推测凑数。
- 同一根因的多个表现合并为一条，避免重复刷屏。
- 无问题时明确写「未发现阻断级问题」，并列出已检查的维度与残余风险。

## 5. 修复边界

- 用户只要求「检视/审查」时，只输出报告，不擅自改代码。
- 用户要求「检视并修复」时，按 P0→P3 顺序在原文件上做最小必要修改，禁止顺手重构无关代码。
- 修复后复跑相关测试或静态检查；无法验证时明确说明验证缺口。
- 修复完成后输出文件变更清单与问题编号对应关系。
